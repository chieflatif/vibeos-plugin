# Profile installer release implementation

Status: implementation complete in the release worktree; integration, independent
review, release commit, tag, and published-clone acceptance remain with the primary
release owner.

## User outcome

The existing profile installer now has a reviewable, pinned install transaction.
It preserves project-owned Claude, Cursor, and Codex customizations, refuses stale
or unsafe plans, carries the controlled-evaluation runtime and guide without
running it, and can exactly roll back an interrupted apply when the target has not
been edited after interruption.

The public commands are:

```text
vibeos analyze --target PATH --source PATH [--profile FILE] [--mode MODE]
vibeos verify --plan FILE
vibeos apply --plan FILE
vibeos recover --plan FILE
```

`verify` validates a pre-apply plan or a completed installed state. `apply` holds a
nonblocking project-local file lock, verifies the plan again after acquiring the
lock, journals every mutation before the first write, and writes a `complete`
install lock only after the generated active-surface check passes. An explicitly
skipped post-check produces `applied-unverified`, not a completed-install claim.

## Bound transaction

The version-2 plan binds:

- the canonical source and target paths, source Git `HEAD`, framework version, and
  installer/helper bytes, plus an explicit scoped `source_worktree_dirty` flag;
- the normalized profile plus exact bytes of an explicit profile file;
- the deterministic generated-output inventory and content hashes;
- project inputs used for name, canon, and validator detection;
- the pre-apply state of every generated output, merge candidate, and install lock;
- the overwrite decision for each output and a hash of the complete plan payload.

Git `HEAD` is reference provenance. `relevant_files_sha256`,
`analyzed_outputs_hash`, and the combined `source_generated_inventory_sha256`
bind the actual source and generated bytes, including a deliberately dirty
development source. The dirtiness read is scoped to the plugin source and the
controlled-evaluation guide; it does not scan unrelated or private files.

Output and recovery paths must be normalized relative POSIX paths. Existing path
components may not be symlinks. Source and target must be distinct, nonnested
canonical directories. Package copying rejects source symlinks and excludes
`__pycache__`, bytecode, tests, and runtime evidence from the controlled-evaluation
package.

Customized generated files and unmanaged existing files remain untouched. Their
new generated bytes go to a separate merge-candidate path. If the normal candidate
already contains unrelated bytes, the installer uses a content-addressed alternate;
it fails closed rather than overwrite two occupied candidates.

## Interruption and recovery

`apply` records each pre-apply file hash and mode, backs up every replaced file,
and records the expected installer-written hash before mutation. `recover` performs
a complete preflight before changing any target byte: it checks the exact plan,
the journal, the backup inventory and every backup hash, then requires each current
path to equal either its pre-apply state or the installer-written state. A user edit
made after interruption therefore stops rollback before any other path changes.
The journal also records parent directories absent before apply. After restoring
all files, recovery removes only those installer-created parents that remain empty,
deepest first; nonempty or concurrently populated directories are preserved.

The transaction lock inode is retained and reused. Concurrent analyze/apply/recover
operations fail without waiting; read-only verification uses a shared lock. Recovery
cleanup rejects symlinked or unexpected backup entries.

Before post-install audit, apply writes a journaled `verifying` lock containing the
exact generated-file inventory. The audit therefore checks fresh-install
instruction surfaces. Only a passing audit permits the atomic `complete` lock.
The recovery journal prebinds both installer-written lock states, so interruption
between recording the final hash and replacing the provisional lock remains exactly
recoverable.
Verification derives the required installed paths, hashes, modes, actions, and
merge candidates from the pinned plan and rejects missing, empty, duplicate,
extra, or fabricated lock rows.

## Controlled evaluation install surface

Every profile mode carries, when present in the release source:

- `.vibeos/scripts/controlled-evaluation.py`;
- Python modules from `.vibeos/scripts/controlled_evaluation/`;
- `.vibeos/controlled-evaluation-guide.md` from
  `docs/CONTROLLED-EVALUATION.md`.

The installer does not invoke the evaluator. Generated `AGENTS.md`, Claude/Cursor
instructions, and project skills point users to
`.vibeos/scripts/controlled-evaluation.py --help`, require project-owner specified
test/check identities and the protected evaluation profile, and state that
`PRE_REVIEW` is not acceptance.

## Reuse decision and evidence

The implementation retained the generic installer at base
`082a011f5804b7d656a75cfa0b5f8d9bd07b2ddc` and adapted only the product-neutral
integrity patterns observed in the newer read-only source at commit
`8efc851f1b33c06bd8b1229687d1180b8135c991`. Team Board extension manifests,
defaults, certification policy, and source-cache requirements were not imported.

The accepted release amendment already refreshed the decisive primary references:
Python atomic rename behavior and subprocess/process-group timeout behavior, plus
pytest exit codes 1 through 6. This installer change added no dependency. The
owned helper modules remain under 300 normally formatted lines.

Verification in the release worktree:

```text

python3 -m pytest -q tests/test_profile_install_release.py tests/test_profile_install.py

```

The release tests use two project identities and a path containing spaces. Negative
coverage includes actual source-byte drift, plan/profile/target/output tampering,
symlink/traversal refusal, occupied merge candidates, installed-state tampering,
an actual SIGTERM during apply, concurrent writer locking, a post-interruption user
edit, a corrupt rollback backup, forged completed locks, malformed installed-state
inventories, fresh-install audit ordering, and clean-versus-dirty source provenance.
The SIGTERM test compares the complete relevant target tree, including directories,
before apply and after recovery; it then verifies and applies the same plan.

## Limits

This work is qualified on the requested macOS/Codex release path. The file lock uses
`flock`, and no cross-OS claim is made. These controls protect against mistakes,
stale inputs, process interruption, and cooperating concurrent installers; they do
not claim hostile same-user isolation. A completed profile install and a
`PRE_REVIEW` controlled-evaluation publication remain separate from owner acceptance
and release approval. No unrelated vNext work order is completed by this change.
